### 2026-06-22 — FR-1 Clarification: PDF URLs Only

**Critical correction:** Desktop app KHÔNG nhận order IDs.

**Actual flow:**
- Web app generates PDFs → upload to S3 → send S3 URLs to desktop
- Desktop app receives: array of PDF URLs (S3 links)
- Desktop workflow: Download PDF from S3 → Render → Print

**Implication:**
- FR-1.1: Request chỉ bao gồm PDF URLs + printer config (KHÔNG có order IDs)
- FR-1.2: PrintJob entity chứa document_url (S3), không có order_id
- FR-1.3: Batch processing = chia nhỏ array of URLs, không có "generate PDF" step

**Responsibility split:**
- **Web app:** Generate PDF, upload S3, send URLs
- **Desktop app:** Download, render (nếu cần), print

### 2026-06-22 — FR-1.3 Clarification: Queue Persistence

**Batch Processing behavior:**
- Khi nhận nhiều PDF URLs → lưu vào database (persist)
- Đẩy vào Queue để xử lý tuần tự
- Queue survive app restart (durable queue)

**Why:** Ensure no job loss nếu app crash/restart giữa chừng. Jobs phải được process eventually.

---

### 2026-06-22 — FR-1.3 Additional Requirements

**Download Strategy:**
- Download theo batch (có thể song song)
- Lưu file vào temp directory
- Sau khi in xong → xóa file temp để tiết kiệm disk space

**Print Status Granularity:**
- Cần phân biệt rõ 3 trạng thái trong print phase:
  1. **SUBMITTED_TO_QUEUE** — Đã đẩy vào print queue của máy in
  2. **PRINTING** — Máy in đang xử lý (printing actively)
  3. **PRINTED** — Đã in xong

**Current issue:** Tất cả đều gộp vào `PRINTING` → không rõ job đang ở đâu

**Solution:** Tách thành 3 trạng thái riêng biệt trong state machine

---

### 2026-06-22 — FR-1.2 State Machine Simplification

**Remove unnecessary states:**
- ❌ `DOWNLOADING` — không cần state riêng
- ❌ `RENDERING` — không cần state riêng
- ❌ `RENDERED` — không cần state riêg

**Simplified state flow:**
`PENDING` → `QUEUED` → `DOWNLOADED` → `SUBMITTED_TO_QUEUE` → `PRINTING` → `PRINTED` → `COMPLETED`

Or on error: → `FAILED` (with retry logic)

**Rationale:** UI chỉ cần biết job đang ở phase nào (downloaded, in queue, printing, done), không cần track từng micro-step. Error handling thông qua retry count, không cần separate error state.

---

### 2026-06-22 — FR-1.2 Further Simplification

**Remove `PRINTED` state:**
- Gộp `PRINTED` vào `COMPLETED` — không cần 2 states riêng
- Sau khi máy in xong → chuyển thẳng sang `COMPLETED` (+ cleanup temp file)

**Final state flow:**
`PENDING` → `QUEUED` → `DOWNLOADED` → `SUBMITTED_TO_QUEUE` → `PRINTING` → `COMPLETED`

Or on error: → `FAILED` (with retry logic)
