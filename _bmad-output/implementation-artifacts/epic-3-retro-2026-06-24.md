## What Went Well (Successes)

### 1. Trait-first design pattern — consistent across all 14 stories
Every story followed: trait definition → concrete implementation → inline tests → integration tests. This enabled easy mocking, clean dependency injection, and implementation swapping (e.g., MuPDF→PDFium).

### 2. Review workflow evolution
Stories 3.1-3.2 had no formal review. From 3.3+, team adopted structured review with [Decision]/[Patch]/[Defer] categories. Quality improved measurably — later stories had fewer logic bugs in review.

### 3. Library swap handled gracefully (Story 3.2)
MuPDF→PDFium decision was documented, rationale clear, downstream stories updated. Zero product impact — users never knew about the change.

### 4. Full pipeline delivered end-to-end
Complete print job lifecycle: S3 download → render → queue → print → retry → cancel → real-time dashboard. Core business value of the entire product.

### 5. RAII temp file management (Story 3.5)
Three-tier cleanup pattern (Immediate/Deferred/Startup) is elegant and robust. Drop trait ensures auto-cleanup. Integration tests thoroughly cover all lifecycle scenarios.

### 6. Event-driven architecture proven
8 domain events map 1:1 with state transitions. Outbox Pattern ensures events persist with aggregates. TauriEventBus wraps domain events → Tauri events cleanly for frontend.

### 7. Team learning visible
Later stories show fewer review findings. Team applied patterns from earlier stories (mutex poison recovery, UUID-based test isolation, Arc<Mutex<Connection>> pattern).

## What Didn't Go Well (Challenges)

### 1. AppContext vs AppContextState confusion (HIGH IMPACT)
**Root cause:** Architecture spec defines `AppContext` struct, but implementation uses `AppContextState` inline struct in `main.rs`. `AppContext` has `todo!()` panic. Every new story must re-discover which struct to use.

**Impact:** Stories 3.3', 3.4', 3.5', 3.7', 3.9 all document this confusion in dev notes. No ADR bridges the gap. Spec ≠ reality.

**Decision:** Fix via ADR + documentation (not full refactor). Document why AppContextState exists, when to use what, and migration path.

### 2. Story 3.8 — 10 patches from AC compliance issues
- `created_at` hardcoded = 0 → date filter broken, all timestamps show 01/01/1970
- `error_message` hardcoded None → failed jobs never display errors
- Retry button references non-existent Tauri command
- Printer dropdown empty due to field name mismatch (`p.printer_name` vs `p.name`)
- Timezone bug in date filtering (UTC vs local)
- Pagination shows "Trang 1/0" when empty
- SUBMITTED_TO_QUEUE missing from filter options

**Root cause:** Pre-merge AC checklist from Epic 2 not applied. @sapo/ui-components API gaps (Table, DatePicker not available) not discovered before implementation.

### 3. String-based error propagation (Stories 3.5', 3.6')
`QueueWorker.process_job()` returns `Result<(), String>`. Story 3.6 uses heuristic string matching for error classification. Fragile, loses type safety, makes testing harder.

**Status:** Identified as refactor target. Deferred to preparation sprint before Epic 4.

### 4. PDFium global init conflict
`pdfium-render` uses `OnceCell` for bindings. Parallel tests cause assertion failures. Requires `PDFIUM_TEST_MUTEX` and `--test-threads=1`. Hidden cost of library swap.

### 5. WDAC policy blocking cargo build
Windows Application Control policy blocks `webview2_com_macros` proc-macro DLL. `cargo build` fails with os error 4551. Workaround: `cargo check` only. Affects production build readiness for Epic 4.

### 6. Epic 2 action items not followed through
5 commitments → 2 partially done, 3 not addressed. Pattern of retrospective commitments not being executed.

## Key Insights & Lessons

1. **Spec ≠ reality requires ADR** — When implementation diverges from architecture spec, document the decision formally. AppContext/AppContextState confusion persisted across 5+ stories because no ADR existed.

2. **Retrospective commitments need tracking** — Without a mechanism to track retro action items between epics, they get forgotten. Need explicit owner + deadline + verification at next epic kickoff.

3. **Library evaluation should happen before story commitment** — MuPDF→PDFium swap was handled well, but the evaluation should have happened during story creation, not during implementation.

4. **@sapo/ui-components gaps need early discovery** — Story 3.8 fell back to HTML table and native date inputs. These gaps should be identified during story creation, not during implementation.

5. **Review workflow is effective** — Structured [Decision]/[Patch]/[Defer] review format works. Quality improved measurably as team adopted it.

6. **Trait-based design scales** — Every story in Epic 3 followed the same trait-first pattern. This consistency reduced cognitive load and enabled clean integration.
